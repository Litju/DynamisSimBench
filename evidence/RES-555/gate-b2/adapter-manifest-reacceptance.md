# RES-555 — expanded adapter-manifest re-acceptance request

Status: **REQUESTED. NOT ACCEPTED. PRODUCTION NOT ACTIVATED.**
This record prepares the exact replacement adapter implementation identity required by owner
condition §3.8. The protected route still pins the owner-accepted 10-file identity from
2026-11-25 and has not been changed. The agent prepared the request; only the owner can accept
the new digests.

## 1. Why this is a new decision

The owner accepted the B2 adapter implementation digests on 2026-11-25:

| Platform | Accepted implementation digest (`.../1`) | Source files |
|---|---|---:|
| Windows x86-64 | `4a907d4262ceca66588188ddcc37894ec488a55f0756886864c89bc5f99827b8` | 10 |
| Linux x86-64 | `7993ac96c91de71a7b5f8770d444c318d6c1283de5b8f0f0d1c615d7c6afe097` | 10 |

That identity covers `reference.ADAPTER_SOURCE_FILES` and `physics.compile_model()`. It does
not cover the inside-sandbox production files added after the B2 probe:

- `dynamisbench/adapters/mujoco/protected_worker.py` - the production worker entry;
- `dynamisbench/adapters/mujoco/protected_contracts.py` - the shared contracts the worker
  imports to reconstruct the identity and validate the view;
- `dynamisbench/execution/protected_bootstrap.py` - the bootstrap that applies the sandbox
  before the worker import.

Those files are measured by the runtime source closure and the profile pins the bootstrap
separately, but they are not bound by the accepted adapter identity. Owner condition §3.8
therefore remains open. The historical 10-file digest is **not** silently reused as the
production identity.

## 2. Proposed replacement identity

The candidate adds a second manifest to the same canonical payload:

```
dynamisbench.mujoco.implementation-identity/2
```

The payload keeps every accepted field and adds
`production_entry_manifest`, a sorted list of repository-root-relative POSIX paths and raw
SHA-256 values. `source_manifest` is unchanged: it remains the 10 adapter-relative entries,
including the verified model digest. The schema version changes because the identity now
binds three more files.

The exact machine-readable request is
[`adapter-manifest-candidate.json`](./adapter-manifest-candidate.json). It contains the
complete canonical payload and both platform digests; it is regenerated by
`python/tools/res555_adapter_manifest.py` and checked for drift by
`python/tests/execution/mujoco/test_protected_adapter_manifest.py`.

## 3. What acceptance would and would not authorize

If the owner accepts both candidate digests, a separate commit would:

1. replace `ADAPTER_SOURCE_FILES`-only identity construction with the schema-2 payload;
2. add `production_entry_manifest` to `reconstruct_implementation_digest` and compare it in
   the supervisor;
3. update `ADAPTER_IMPLEMENTATION_DIGESTS` and re-qualify the pinned reference on both
   platforms.

Acceptance of the digests would **not** activate the protected route. The API, CLI, desktop
shell and workbench still cannot reach it; no environment variable enables it; no native
output, canonicalization, assessment or seal is added. ADR-027 remains separate.
